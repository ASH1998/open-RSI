### Reading the outcomes

For each teacher report unique tasks solved by greedy+sample and greedy+repair, including repair-only, sample-only, both and neither, plus recovery counts among greedy failures and by category. The causal contrast combines access to first code, verdict and a revision instruction; it cannot isolate the effect of the failure kind alone. Count shared greedy work once when reporting expenditure. Different prompt lengths can change actual input tokens even at matched ceilings. Missing infrastructure evidence leaves an incomplete experiment.

A child comparison tests original versus learned teaching **under repair**. It does not test the effect of repair on trained children unless children are also trained from the independent-sampling labels. With both children trained, report each child's gain over the same starting student, learned-teacher child minus original-teacher child on the same fresh tasks, and individual retention regressions. Report task-level discordances and the denominator. A small single-seed comparison supports at most a one-step finding. Keep the original parent selected regardless of the result.

### Native partial cohort review

The native builder reports only six admissible validation rows before further calibration. Consequently a fresh eight-task block made from native training rows must be described as a project-held-back training-source block.

I compared the draft contract list against the pinned raw training sources and the 284 exposures. Two dispositions should be made before integrating supplemental data:

- **Quarantine 840 against exposed 636.** Both functions have exactly the same name and argument list, `Check_Solution(a,b,c)`, return `"Yes"`/`"No"`, and ask for a relationship between the two roots of a quadratic. Only the requested relationship/coefficient predicate changes. This is the sort of template variant that the project's earlier predicate/complement quarantines were intended to remove.
- **Quarantine 829 against exposed 862 and 946.** 862 computes the most common words in a string and 946 computes ranked element/count pairs using `Counter(...).most_common(n)`. 829 selects one element by the second frequency rank (slightly different tie handling) from a sequence of strings. On the unique-count portion this reduces to the previous ranking plus projection and input formatting. Merely changing the source ID and specifying tie behavior does not merit a fresh text slot.
- 832 and exposed 944 both extract decimal runs with a regex. 944 returns the position of the first run, whereas 832 parses all values and takes a numeric maximum. Their output targets and decisive boundaries differ, so sharing this parsing primitive alone does not justify exclusion here.

The supplemental APPS selection, if accepted, needs a separate source lineage, native train split and deterministic function-IO conversion. An APPS solution embedded in the source is only one oracle: check both the native test pairs and independent expected outputs, and reject tasks whose references require unavailable I/O, packages or an incompatible harness. Audit all final candidates against both the 284 and the admitted MBPP train/holdout tasks. Report native and supplemental outcomes separately by source; adding APPS only on the training side changes what the held-back MBPP evaluation measures.
