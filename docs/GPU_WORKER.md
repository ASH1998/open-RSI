# Modal GPU worker

`rsi/modal_workers.py` defines an `open-rsi` Modal App and three remote functions. Importing it does not launch compute. The parent controller is responsible for budget reservations and for invoking stages serially. The $250 project ceiling is not enforced by this worker alone.

Each function uses one A10, exactly two requested/maximum CPU cores, 16 GiB requested/maximum memory, a single-container maximum, zero warm containers, a 15-second scale-down window, a 600-second startup limit, a 1,800-second execution limit, and zero configured input retries. Generated code is never executed in these workers.

Only `.py` source in the `rsi` package and `requirements-gpu.txt` are included; automatic source inclusion is disabled on both the App and functions. The requirements file is the image's installation input. The worker neither reads `.env` nor receives user-supplied provider/W&B secrets. Public model downloads use `token=False` and disable implicit Hub tokens. HF/Torch caches and adapters persist on the `open-rsi-artifacts` Volume mounted at `/artifacts`. Each call reloads the Volume before checking artifact paths, so warm containers see preceding committed stages. Modal supplies its own runtime authentication; this is not an untrusted-code execution environment.

## API

- `smoke(request={})`: loads the pinned model and generates a maximum of 96 new tokens for one simple coding prompt.
- `generate(request)`: accepts `prompts=[{"id": "...", "prompt": "..."}]`, `max_new_tokens` (default 512, maximum 768), `max_input_tokens` (default 2048, maximum 4096), `seed`, `temperature` (default zero/greedy), and optional `adapter_path`. Returns `outputs` containing text, token counts, token-limit flags, and per-item runtime. Maximum 64 prompts per call.
- `train(request)`: accepts `examples=[{"prompt": "...", "completion": "...", "verified": true}]`, `run_id`, `max_steps` (default 40, maximum 200), `gradient_accumulation` (default 4), `max_length` (default 1536), `learning_rate` (default 0.0001), and optional `resume_checkpoint`. Maximum 256 examples. Caller must actually verify targets; the boolean is an interface assertion, not a verifier.

Prompt/completion strings must be nonempty and at most 30,000 characters each. Training text totals at most 2,000,000 characters. Prompt IDs, when supplied, are strings of at most 200 characters. Numeric bounds reject booleans, NaN, and infinity. Training allows `gradient_accumulation=1..8`, `max_length=64..2048`, `checkpoint_every=1..50` (default 10), and `learning_rate=1e-8..5e-4`. `seed` defaults to 42 and is an integer in `0..2**31-1`.

Generation checks a 1,500-second internal deadline between prompts and passes the remaining duration to Transformers generation. On that deadline it returns `status="generation_time_limit"` and available outputs, including an item-level `hit_time_limit`. This is incomplete even if an output exists for every prompt. Training checks its 1,400-second internal deadline between microbatches. These are cooperative checks: a model load, CUDA operation, or Volume commit can overrun them. Modal's 1,800-second execution timeout is the outer bound and can kill the call without a result. Startup/build/idle time is separate. Limits of one container apply separately to each function; the parent must serialize stages to enforce the project spending policy.

All requests default to and only accept `openbmb/MiniCPM5-2B` at revision `f97400052a43d642bbc6e9975e2397e3ae6a6b52`. Model changes require an explicit code review. All successful responses include installed direct/transitive package versions, GPU name, peak allocated GPU memory, CUDA version, elapsed execution time, and base identity. Runtime excludes remote startup/build/idle billing; use the controller's conservative cost ledger.

## Learning implementation

Inference and training both load an NF4 double-quantized base with bfloat16 computation. The initial adapter uses rank 8, alpha 16, zero dropout, and all attention/MLP projections. A small AdamW loop trains completion-only causal loss; it does not require a TRL installation. The original model chat template is used for both phases with `enable_thinking=False`. The training encoder checks that the full conversation begins with exactly the same token prefix used by inference. Prompt tokens receive label `-100`; assistant completion and conversation terminator receive supervision. Oversized examples fail instead of truncating a verified repair.

The model's official fine-tuning recipe establishes PEFT support, while the quantization settings follow the PEFT QLoRA guide. The custom loop keeps the pilot's training state and masking explicit. This is an implementation choice, not a claim of equivalence to every TRL default. [OpenBMB recipe](https://github.com/OpenBMB/MiniCPM/blob/main/docs/finetune/trl.md), [PEFT quantization](https://huggingface.co/docs/peft/developer_guides/quantization)

Checkpoints contain the adapter, optimizer, step, loss history, Torch CPU/CUDA RNG state, and a hash of the examples/settings, worker source, and direct installed package versions. Data ordering is deterministically shuffled from the fixed seed and indexed by the restored step. No learning-rate scheduler is used. Resume checks file inventory/checksums and the fingerprint and only accepts a complete checkpoint for the same run ID. AdamW moments follow their parameter device; non-capturable scalar step counters remain on CPU. Partial accumulation is discarded on the internal deadline and the step-start RNG state restored.

A completed or time-bounded run returns `adapter_path`, `checkpoint_path`, `steps_completed`, `losses`, `examples_count`, `supervised_tokens`, and `status`. A `checkpointed_time_limit` result is incomplete and must not be promoted. `max_steps` is the total optimizer-step target, including saved steps, and may increase on resume within the 200-step cap. The controller must reserve each resumed launch separately.

Snapshots live at `/artifacts/adapters/<run_id>/checkpoints/step-<step>-<unique-id>`. Each is written in a pending directory, completed with checksums, renamed, and committed before atomically replacing and committing `latest_checkpoint.json`. Previous snapshots are retained. After an unexpected kill, use the latest committed pointer or inspect complete snapshot manifests; never resume a `.pending-*` directory. Pass the exact returned `checkpoint_path` as `resume_checkpoint`. Adapter export paths are also unique and opaque; callers must use `adapter_path` from a returned completed result. Export existence alone does not prove success. Remote crash/Volume persistence semantics still need validation. No automatic retention cleanup is implemented.

## Validation boundary

Reviewed locally November 4, 2026 using the project's Python 3.13 environment and Modal 1.6.3. Passed: AST syntax, credential-free import with socket connections blocked, unhydrated resource declarations, requirements/audit-tuple parity, enumeration of the declared local source mounts (only package Python files and the requirements file), and synthetic helper checks for numeric bounds, adapter path traversal rejection, completion-only masking, prefix mismatch rejection, and sequence-length rejection. The installed Modal SDK accepts all declared resource arguments. These are local checks, not a GPU test suite.

The initial review did not install GPU packages or launch remote work. The main chat subsequently reported that its A10 smoke loaded the model but failed when constructing a tensor from the chat-template result (`runs/20261104T070236Z-smoke-75a7ca/report.json`). A10 remains selected after unavailable L4 capacity. Following the tokenizer fix, the main chat completed inference/baseline and training. The training report `runs/20261104T071521Z-train-b77c8e/report.json` records 20 optimizer steps on four examples, 76.21 worker seconds, and 4,098,846,720 peak allocated GPU bytes (3.82 GiB). This verifies that training executed, not that the candidate improved. Optimizer restoration and uninterrupted-versus-resumed equivalence remain untested. Transitive versions are recorded after installation but not locked.

The November 4 integration fix reproduced this on CPU with Transformers 5.22.1, Tokenizers 0.23.3, and the real tokenizer at the pinned revision. `apply_chat_template` defaults to `return_dict=True`, producing `BatchEncoding`; integer indexing yields a `tokenizers.Encoding`, not a token ID. Both generation and training now explicitly pass `return_dict=False`. No dependency pins or public interfaces changed.

Five regression tests in `tests/test_tokenizer.py` passed, including three real-tokenizer tests loaded strictly from the SSD cache. The smoke prompt produces 31 integer IDs; the simple `add` completion has 13 supervised tokens. Tests confirm the exact inference prefix is masked with `-100`, while completion plus `<|im_end|>\n` is supervised, covering ordinary code, leading newlines (stripped by the model's own template), code fences, and Unicode. Oversized examples are rejected. The tokenizer was fetched publicly with `token=False`; no weights, credentials, or remote jobs were used by this fix. Jinja2 3.1.6 and MarkupSafe 3.0.4 were added only to the project-local CPU environment so the template could run.

To rerun the cached CPU checks from the SSD root, set `HF_HOME="$PWD/.cache/huggingface"`, `HF_HUB_OFFLINE=1`, `HF_HUB_DISABLE_IMPLICIT_TOKEN=1`, `MODAL_CONFIG_PATH="$PWD/work/nonexistent-modal-config.toml"`, `PYTHONDONTWRITEBYTECODE=1`, and `RSI_TEST_REAL_TOKENIZER=1`, then run `.venv/bin/python -m unittest discover -s tests -p test_tokenizer.py -v`. Without the opt-in variable, the three real-tokenizer tests are skipped and the two contract tests run.

The subsequent evaluation (`runs/20261104T071729Z-evaluate-0d688c/report.json`) failed during adapter-directory validation before model loading. Local simulation reproduced a defect: resolving only the candidate and comparing it to the unresolved `/artifacts/adapters` rejects a valid child when the mount or its parent is a symlink. The main chat's completed CPU diagnostic (`runs/20261104T072219Z-artifact-inspection-dc77f6/report.json`) confirmed the exact cause: `/artifacts` is a symlink into `/__modal/volumes/`, and the adapter directory exists within that canonical root. The reported paths fail the old comparison and pass the corrected one. `_adapter_path` now resolves both candidate and allowed root, while preserving the required public path prefix and rejecting symlink escapes, traversal, the root itself, and missing/non-directory targets. Checkpoint resume compares canonical parent paths too. Seven CPU regression tests in `tests/test_worker_paths.py` passed using temporary directories exclusively under project `work/`. This review launched no remote work; main coordinated the diagnostic. Error messages now distinguish containment rejection from a missing directory.

The corrected evaluation completed in `runs/20261104T072356Z-evaluate-92cbe2/report.json`. The existing adapter loaded successfully. Parent and candidate used the same task hash, decoding settings, packages, and A10 hardware. Train success changed from 4/16 to 6/16, while development success fell from 7/8 to 5/8. The parent was retained and the candidate was not promoted. These results do not establish self-improvement.

The completed integration verifies generation, a 20-step training run, artifact saving and SSD export, adapter loading, and evaluation. Main reports all 60 local tests passing. This does not validate interruption recovery, optimizer restoration, or uninterrupted-versus-resumed equivalence. Resume still checks the complete worker-source fingerprint, so checkpoints created before the path fix cannot be resumed with the new source without a separately reviewed migration; any future equivalence check needs a fresh same-source checkpoint.
